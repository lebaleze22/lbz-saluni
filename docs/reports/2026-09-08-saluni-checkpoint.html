01

Current assessment

SALUNI is LBZ's salon management application for the Cameroon market. The immediate use case is replacing Caprice D'Ebène's paper activity and cash register with a digital record of clients, services, staff, receipts, and expenses.

Checkpoint conclusion: the current code is a buildable MVP with prepared client installation tooling. The next milestone is an evidenced release and installation rehearsal, followed by acceptance on the salon's Mac.

Established in this review

  • Register, services, expenses, reports, staff, and job-title workflows exist in application code.
  • Unit tests, TypeScript, ESLint, and the production Next.js build pass locally.
  • Client Compose, initialization, update scripts, and multi-architecture release automation are present.
  • The starting working tree was clean at the recorded Git commit.

Evidence still needed

  • A published release with downloadable images and an installation bundle.
  • Current database isolation and fresh-install results against a disposable stack.
  • Installation, sign-in, and daily workflows on the intended Mac.
  • Recovery from backup and an update that preserves operational data.

Scope: local repository, source inspection, recorded architecture decisions, and commands run on 8 September 2026. This review did not inspect salon production records, GitHub release status, or a remote deployment. “Implemented” describes source coverage; it does not imply every workflow was exercised in a browser today.

03

Implemented product workflows

Area / route Current behavior Boundary
Activity register
/register		 Daily chronological visits, date and staff filters, client name with optional phone and sex, reservation or walk-in origin, staff selection, multiple services, per-visit prices, and a recorded payment. The payment must equal the total of service lines. No visit correction or refund action is exposed by the inspected register data layer.
Services
/services		 Create and edit services, reference prices, categories including inline category creation, activation, archiving, and restoration. Changing the reference price does not overwrite prices already saved on visit lines.
Expenses
/expenses		 Create, edit, archive, and restore an expense with description, positive integer FCFA amount, date, optional category, and recording staff member. Expenses are independent of visits. Archived expenses are excluded from report expense totals.
Reports
/reports		 Weekly, monthly, and quarterly summaries: receipts, expenses, net result, payment methods, staff and service breakdowns, visits, service volume, and new/returning clients. PDF and Excel routes are implemented. Net result is the arithmetic of recorded receipts minus recorded expenses. Payroll and commissions are not automatically booked.
Staff
/staff
/staff/nouveau		 Owner creates staff profiles, assigns multiple job titles and a primary title, captures administrative and pay information, optionally provisions a system-role account, and controls status. The current edit function updates name and job assignments. It does not provide full editing of the rich administrative or pay profile.
Job titles
/job-titles		 Owner manages salon-specific job titles, with create/edit and status operations. A title describes work performed. Application permissions come from system/account roles.

Register behavior that matters in daily use

Each visit is saved with its client, staff member, service lines, and payment within one tenant transaction. Prices must be positive integers, duplicate services in a visit are rejected, and the paid amount must match the line total. Client matching uses phone and/or a case-insensitive name match; people with the same name and no phone can still be confused by this best-effort matching.

Cash, Orange Money, and MTN MoMo are recorded payment methods. No payment collection, operator API, or payment webhook is implemented in this checkpoint.

Reports and exports

Revenue is summed from payments; service breakdowns use saved visit-line prices; staff breakdowns use receipts for that staff member's visits. The report periods follow the Africa/Douala day boundary, with weeks beginning on Monday. Both exports use the same report data function as the screen.

The Excel workbook contains Synthèse and Prestations sheets. Detail rows represent individual service lines and repeat the visit's total on each line; summing that repeated total across all detail rows would overcount multi-service visits. The PDF generator includes summaries and service details, with page numbering.

Sources: register data layer, register validation, staff data layer, report aggregation, Excel export, PDF export.

Access, identity, and tenant isolation

Identity Operational screens Staff / job titles Current meaning
Owner
users.role = owner		 Allowed Allowed Salon owner, with full operational parity and team administration.

users.role = salon_admin		 Allowed Denied Runs daily salon operations.

users.role = manager		 Denied by current guard Denied Account provisioning exists; a usable Manager application area does not yet exist.

staff.systemRole = none		 No login No login Selectable service provider, with a staff record and job titles.

The client initializer gives the Owner a linked technical Staff profile whose systemRole is manager. The Owner still has users.role = owner and therefore passes the Owner guard. This technical profile is distinct from a normal Manager user account.

  1. Session verification: read the session cookie and verify the access-token signature and expiry through jose. Local GoTrue uses HS256; the managed setup supports ES256 through a cached remote key set.
  2. Application identity: resolve the user and Staff profile from the database. Admin pages require an active, non-deleted Owner or Director and an active, non-deleted linked Staff profile.
  3. Tenant transaction: use the restricted app_runtime connection and transaction-local app.tenant_id, app.role, and app.user_id.
  4. Database enforcement: SQL policies control row access. Composite foreign keys include the tenant ID on register relationships to prevent references to another tenant's records.

The privileged adminPrisma connection is used for identity bootstrap and account provisioning/cleanup in the inspected staff flow. Business operations otherwise use tenant transactions. These privileged call sites are a concrete review boundary when extending account management.

The register's staff selector explicitly excludes administrative identity-document fields, and a unit test protects that projection. Staff identity numbers are still captured as ordinary stored fields; no field-encryption implementation was found in the inspected creation path.

Verification limit: source inspection confirms the policies and tenant-aware relationships are present. The database isolation suite was not rerun in this review because a usable local Docker stack could not be confirmed.

Sources: access guards, tenant session transactions, JWT verification, tenant-scoped register foreign keys, Owner client-write parity.

06

Data model and business rules

The current Prisma schema defines 12 business models. The repository contains 24 migration directories, including manually written security policies and constraints that Prisma's model declarations alone do not express.

Model group Tables and relationships
Salon and access Tenant is the salon boundary. User links an application account to its Auth identity and tenant.
Team Staff optionally links to a User. JobTitle and StaffJobTitle support multiple titles and a primary assignment.
Customers Client stores a salon customer and optional contact/demographic fields.
Catalogue ServiceCategory groups Service records with reference prices.
Activity and receipts Appointment is a visit; AppointmentService captures individual services and their actual prices; Payment records a visit receipt.
Outgoings Expense belongs to a tenant and a recording Staff member, independently of visits.
  • Currency: monetary amounts use integer FCFA values. Commission rates use a decimal percentage; storing a rate does not calculate a payroll.
  • Time: the register and report helpers use Africa/Douala day boundaries.
  • Lifecycle: activation and soft deletion are separate fields. Archive/restore behavior is implemented in supported management flows; Staff restoration clears deletion but does not automatically reactivate the profile.
  • Relationships: tenant-aware foreign keys protect register parent/child consistency. Removing a staff job-title assignment deletes that association row.
  • Source of truth: use the current Prisma schema together with SQL migrations for implementation decisions.

Sources: current Prisma schema, date helpers. An existing HTML ERD is available; its agreement with every current migration was not revalidated for this report.

07

macOS client deployment

The prepared distribution avoids building SALUNI on the client Mac. A release workflow builds four SALUNI images for linux/amd64 and linux/arm64: core-api, tooling, postgres, and nginx. GoTrue uses its separately pinned image.

Release path present in the repository

  1. A v* tag or a manual workflow dispatch selects an image version.
  2. The quality job installs dependencies, runs unit tests, and checks TypeScript.
  3. The image matrix builds and publishes to the configured GHCR image root.
  4. The package job creates saluni-client-<version>.tar.gz and its SHA-256 checksum. A tag-triggered run also attaches them to a GitHub release.

The image root is currently ghcr.io/lebaleze22/lbz-saluni. Published packages must be accessible to the Mac. This report confirms the workflow definition, not that a specific version is already available in GHCR.

Installer sequence

scripts/client-install/install-macos.sh checks Docker and OpenSSL, obtains tooling, creates random local database/Auth secrets, writes .env.client.local with restricted file permissions, pulls images, starts PostgreSQL and Auth, applies migrations, configures the runtime role, starts SALUNI, checks Auth/login endpoints, provisions the Owner, imports the catalogue, and checks installation counts.

These are target counts for a fresh installation, not observed counts from the salon database today. The initializer requires an Owner password of at least 14 characters, rejects known development defaults, and performs a real password sign-in check. The Owner then creates the Director and salon team through the application.

Updates and data continuity

update-macos.sh selects a version, pulls images, applies migrations, configures the runtime role, and restarts the application while retaining the named PostgreSQL volume. The script does not call the fresh-install initializer or import. It ends with container status; it does not perform the installer's Auth/login HTTP checks or create an automatic backup.

The existing installation guide documents manual database backups and calls for testing restoration on a separate installation. An update and restore rehearsal remains an acceptance step. Routine local operation is designed to continue without Internet after image download, with Docker Desktop running on the Mac.

Prepared operator entry points

Run these from the extracted client bundle on the intended Mac after satisfying the installation prerequisites. The version below is a placeholder. 

./scripts/client-install/install-macos.sh

docker compose --env-file .env.client.local -f docker-compose.client.yml ps

./scripts/client-install/update-macos.sh <published-version>

Use the installer for initial setup/recovery and the update script for an operating salon. Re-running initialization can reset the Owner password supplied to it; fresh-install zero-count verification is not a general health check after real activity has been recorded.

Sources: release workflow, installer, updater, initializer, count verifier, existing installation guide.
