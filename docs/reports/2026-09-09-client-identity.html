One client record, four identity checks

Name, phone, email and sex are compared together within each salon.

Matching rules

Situation Result
All four fields match Client creation and edits into a duplicate are blocked. The register reuses an exact active match when contact details are present.
Same name, different phone, email or sex A separate client record is allowed.
Shared phone or email, different name A separate record is allowed; phone alone no longer links a visit.
Matching record has no phone or email Select the existing client explicitly, or supply distinguishing contact details. The register does not silently assume identity.
Archived match Restore the existing record instead of creating a replacement.
Multiple legacy matches The register requires an explicit client selection.

Missing fields compare as empty values. A difference in any one field makes the four-field combination distinct. These are duplicate-entry checks, not proof of a person's identity; incomplete or mistyped details can still describe the same person differently.

Normalization and concurrency

Name comparisons ignore casing and repeated whitespace. Email comparisons ignore casing and surrounding whitespace. Phone comparisons ignore punctuation and reconcile Cameroon national numbers with +237 and 00237 formats. Other international country codes are retained.

Client creation, identity edits and register submissions share a transaction-level lock per salon, preventing simultaneous application submissions from both creating the same identity. Checks include archived records and remain inside tenant-restricted database transactions. This is application enforcement; privileged direct database writes do not pass through these checks.

What changed on screen

The register now includes an optional email field. Existing-client choices display phone, email and sex where available. Both client creation and register forms explain the four-field rule.

Existing records and histories are preserved. No automatic merge or deletion is performed, and this update requires no schema migration.
